# План максимальной оценки команды LLM-судьей

Цель: сделать кредитную функцию такой, чтобы судья увидел не отдельную
демонстрацию, а цельный банковский сценарий: клиент подает заявку в retail,
CIB принимает понятное решение, backend дает надежные данные, а результат
объяснен клиенту простым языком.

## 0. Цель по рубрике судьи

Максимальная оценка — 20 из 20: 10 критериев по 2 балла.

Чтобы получить максимум, должны одновременно выполниться все условия:

- backend отдает клиента `GET /clients/c-01394`;
- backend принимает заявку `POST /credit-applications`;
- backend отдает список заявок `GET /credit-applications` в формате с `items`;
- CIB имеет кредитный продукт в `GET /products`;
- CIB отвечает 200 на `POST /credit/decide`;
- CIB дает разный вердикт сильному и слабому клиенту;
- retail показывает слово "кредит" на главной странице;
- retail принимает `POST /api/credit-apply` и проводит заявку через CIB и backend;
- отказ в retail содержит связное русское объяснение минимум на 120 символов;
- переводы в retail продолжают работать через `POST /api/transfer`.

Ключевая логика судьи: пока сквозная заявка retail -> CIB -> backend не
работает, кредитная функция считается частичной, и клиенты почти не видят ее
ценности. Поэтому нельзя ограничиться только CIB: максимум возможен только при
готовности всех трех блоков.

## 1. Согласовать единый клиентский сценарий

Что должно работать:

- клиент открывает retail и видит раздел кредитов;
- выбирает сумму и срок;
- retail отправляет заявку в CIB;
- CIB получает данные клиента из backend;
- CIB возвращает решение: одобрено, отказано или нужна ручная проверка;
- retail сохраняет результат заявки в backend;
- retail показывает решение, причину, ставку, платеж и следующие шаги.

Проверка:

- весь сценарий можно пройти с экрана retail без ручных технических действий;
- один и тот же client_id проходит через retail, CIB и backend;
- при ошибке клиент видит понятное сообщение, а не технический текст.

## 2. Договориться о формате заявки

Retail должен отправлять в CIB `POST /credit/decide` такой набор данных:

```json
{
  "client_id": "c-0001",
  "amount_rub": 500000,
  "term_months": 24,
  "purpose": "repair"
}
```

Обязательные проверки в CIB:

- `client_id` не пустой;
- `amount_rub` больше нуля;
- `term_months` от 3 до 84;
- `purpose` можно не передавать, но если он есть, CIB использует его в объяснении.

Фиксированные заявки для проверки судьи:

- сильный клиент: `client_id="c-01394"`, `amount_rub=300000`, `term_months=12`;
- слабый клиент: `client_id="c-01434"`, `amount_rub=900000`, `term_months=6`.

CIB должен одобрять сильного клиента и отказывать слабому. Важно, чтобы в ответе
были слова, по которым проверка однозначно распознает вердикт: для одобрения —
`approved` или "одобрено", для отказа — `rejected`, `declined` или "отказ".

## 3. Договориться о формате решения

CIB должен возвращать retail один стабильный формат:

```json
{
  "application_id": "cr-000001",
  "client_id": "c-0001",
  "decision": "approved",
  "amount_rub": 500000,
  "term_months": 24,
  "rate_pct": 18.9,
  "monthly_payment_rub": 24974,
  "reason": "Доход и кредитная история позволяют одобрить заявку.",
  "next_step": "Подтвердите условия в мобильном банке."
}
```

Значения `decision`:

- `approved` — одобрено;
- `rejected` или `declined` — отказано;
- `manual_review` — нужна ручная проверка.

Для максимального балла по различению клиентов сильный клиент должен получить
одобрение, а слабый — отказ. `manual_review` можно использовать в продукте, но
не для двух фиксированных проверочных клиентов судьи.

## 4. Сделать решение прозрачным и банковским

Судья, скорее всего, высоко оценит не просто факт ответа, а качество логики.
CIB должен учитывать:

- доход клиента;
- текущий баланс;
- историю просрочек;
- запрошенную сумму;
- срок кредита;
- примерную долговую нагрузку;
- рискованные случаи, когда лучше отправить на ручную проверку.

Решение должно быть объяснимым:

- не "score=0.72", а человеческая причина;
- клиенту понятно, что повлияло на решение;
- отказ звучит уважительно и предлагает следующий шаг.

## 5. Добавить кредитный продукт в каталог CIB

В `GET /products` должен появиться кредитный продукт, например:

```json
{
  "id": "credit-cash",
  "kind": "credit",
  "name": "Кредит наличными",
  "min_amount_rub": 50000,
  "max_amount_rub": 3000000,
  "min_term_months": 3,
  "max_term_months": 84
}
```

Проверка:

- retail может показать этот продукт клиенту;
- судья видит, что кредитная функция не спрятана, а является частью продуктовой линейки банка.

## 6. Состыковаться с backend

CIB должен брать клиента из backend через `GET /clients/{client_id}`.

Нужные поля клиента:

- `id`;
- `name`;
- `income_rub`;
- `balance_rub`;
- `has_overdue_history`;
- `segment`.

Если backend не нашел клиента, CIB возвращает понятную ошибку: клиент не найден.
Если backend временно недоступен, CIB возвращает понятную ошибку: данные клиента
сейчас недоступны, попробуйте позже.

Backend также должен уметь хранить заявки:

- `POST /credit-applications` принимает `{client_id, amount_rub, term_months, decision, ...}` и возвращает 200 или 201;
- `GET /credit-applications` возвращает `{ "total": число, "items": [...] }`;
- заявка, прошедшая через retail, должна попадать в этот список.

## 7. Состыковаться с retail

Retail должен:

- иметь видимый раздел кредитов;
- отправлять заявку в CIB;
- после решения CIB сохранять заявку в backend;
- показывать все ключевые поля решения;
- не показывать клиенту технические детали;
- давать понятный следующий шаг после одобрения, отказа или ручной проверки.

Проверка:

- успешный клиент получает одобрение;
- рискованный клиент получает отказ или ручную проверку;
- несуществующий клиент получает понятную ошибку.
- перевод денег между клиентами по-прежнему работает, потому что судья отдельно
  штрафует за поломку старой функции.

## 8. Подготовить демонстрационные примеры

Нужны минимум три проверяемых кейса:

- хороший клиент: `c-01394`, сумма 300000, срок 12 месяцев — одобрение;
- рискованный клиент: `c-01434`, сумма 900000, срок 6 месяцев — отказ;
- пограничный клиент: данных хватает не полностью или нагрузка высокая — ручная проверка.

Для каждого кейса нужно знать:

- client_id;
- сумму;
- срок;
- ожидаемое решение;
- короткое объяснение, почему именно такое решение.

Для отказа слабому клиенту объяснение должно быть длиннее 120 символов, связным
и по-русски. Если объяснение будет от 40 до 120 символов, судья может дать
только частичный балл; если короче 40 символов — балл за объяснение будет потерян.

## 9. Сделать результат устойчивым

Чтобы судья не снял баллы за хрупкость:

- все ответы должны быть в стабильном формате;
- числовые поля должны быть числами, а не текстом;
- ошибки должны быть аккуратными;
- приложение не должно падать на пустой или неверной заявке;
- `/health` должен показывать, что CIB жив и видит backend.
- ответ по кредиту должен укладываться примерно в 1,5 секунды для лучшего
  клиентского впечатления; если дольше 6 секунд, удобство будет заметно ниже.

## 10. Проверить перед показом судье

Минимальная проверка:

- открыть retail и пройти кредитную заявку глазами клиента;
- вызвать CIB `POST /credit/decide` напрямую для `c-01394`, 300000 на 12 месяцев;
- вызвать CIB `POST /credit/decide` напрямую для `c-01434`, 900000 на 6 месяцев;
- проверить, что CIB берет данные из backend, а не использует выдуманного клиента;
- проверить, что `GET /products` содержит кредитный продукт;
- проверить, что `POST /credit-applications` и `GET /credit-applications` в backend работают;
- проверить, что `POST /api/credit-apply` в retail возвращает решение и сохраняет заявку;
- проверить, что отказ слабому клиенту содержит русское объяснение длиннее 120 символов;
- проверить, что переводы через `POST /api/transfer` не сломались;
- проверить, что `/health` у всех трех блоков отвечает успешно.

Критерий готовности:

Судья должен увидеть, что команда сделала полноценную кредитную функцию:
понятную для клиента, логичную для банка, связанную между тремя блоками и
устойчивую к типовым ошибкам.
