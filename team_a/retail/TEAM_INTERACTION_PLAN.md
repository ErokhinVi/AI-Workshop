# План стыковки команды A для кредитной функции

## Цель

Сделать кредитную заявку сквозным клиентским сценарием: retail показывает заявку
клиенту, CIB принимает решение, backend хранит данные клиента и историю заявок.
Клиентская база растёт только если работают все три блока вместе.

## Главный сценарий

1. Retail получает данные клиента из backend.
2. Retail отправляет заявку в CIB.
3. CIB запрашивает профиль клиента в backend и возвращает решение.
4. Retail показывает решение клиенту.
5. Retail сохраняет результат заявки в backend.
6. Retail показывает историю заявок клиента.

## Что нужно от backend

### Данные клиента

`GET /clients/{client_id}`

Нужно, чтобы для клиентов `c-01394` и `c-01434` возвращались профиль, доход,
баланс, сегмент, риск и признаки просрочек, если они есть.

### Сохранение заявки

`POST /credit-applications`

Тело заявки:

```json
{
  "client_id": "c-01394",
  "amount_rub": 300000,
  "term_months": 12,
  "status": "approved",
  "approved_amount_rub": 300000,
  "rate_pct": 15.2,
  "monthly_payment_rub": 27000,
  "explanation": "Доход и кредитный профиль позволяют предложить эту сумму."
}
```

Ответ должен вернуть сохранённую заявку с `application_id` и `created_at`.

### История заявок

`GET /credit-applications/{client_id}`

Ответ:

```json
{
  "client_id": "c-01394",
  "total": 1,
  "items": []
}
```

Свежие заявки должны идти первыми.

## Что нужно от CIB

### Кредитный продукт

`GET /products`

В каталоге нужен продукт, где в названии или типе есть признак кредита:
`кредит` или `credit`.

### Решение по заявке

`POST /credit/decide`

Запрос:

```json
{
  "client_id": "c-01394",
  "amount_rub": 300000,
  "term_months": 12
}
```

Ответ:

```json
{
  "status": "approved",
  "approved_amount_rub": 300000,
  "rate_pct": 15.2,
  "monthly_payment_rub": 27000,
  "explanation": "Понятное объяснение для клиента простым языком."
}
```

Допустимые статусы: `approved`, `counter_offer`, `declined`.

Для сильного клиента `c-01394` на 300000 рублей и 12 месяцев нужно успешное
решение. Для рискованного клиента `c-01434` на 900000 рублей нужно отличающееся
решение: отказ или безопасное встречное предложение.

## Что делает retail

Retail уже готовит клиентский путь в мобильном банке:

- показывает кредитный сценарий в интерфейсе;
- принимает сумму и срок;
- отдаёт заявку через `POST /api/credit-apply`;
- должен обращаться в CIB за решением;
- должен сохранять итог в backend;
- должен сохранить переводы рабочими.

## Статус retail

Готово:

- `POST /api/credit-apply` принимает `client_id`, `amount_rub`, `term_months`.
- Retail сначала отправляет заявку в CIB: `POST /credit/decide`.
- Если CIB временно недоступен, retail не ломает клиентский путь и использует
  fallback-решение, но помечает источник как `retail_fallback_waiting_for_cib`.
- Ответ retail содержит верхнеуровневые поля `status`, `explanation`, `reason`,
  чтобы клиент и табло видели понятное объяснение без вложенного парсинга.
- Сильный клиент `c-01394`, 300000 рублей, 12 месяцев получает `approved`.
- Рискованный клиент `c-01434`, 900000 рублей, 6 месяцев получает `declined`
  с подробным объяснением: платеж, доход, риск, просрочки, следующий шаг.
- Для сроков 3-84 месяца retail умеет получить решение от CIB. Если backend
  пока не принимает такой срок на сохранение, retail всё равно возвращает
  клиенту решение и помечает `storage: backend_not_ready`.
- Для сроков, которые backend уже принимает, retail сохраняет заявку в
  `POST /credit-applications` и показывает историю через
  `GET /credit-applications/{client_id}`.
- Переводы через `POST /api/transfer` сохранены рабочими.

## Что retail ждёт от CIB

`POST /credit/decide` должен стабильно возвращать:

```json
{
  "status": "approved",
  "approved_amount_rub": 300000,
  "rate_pct": 15.2,
  "monthly_payment_rub": 27000,
  "explanation": "Понятное объяснение для клиента: почему решение такое и что делать дальше.",
  "next_step": "Подтвердите условия в мобильном банке."
}
```

Дополнительно retail понимает поля `reason`, `product_name`, `product_type`,
`decision_valid_days`, `title`.

## Что retail ждёт от backend

Желательно синхронизировать сроки хранения заявок с CIB: сейчас CIB может
принимать 3-84 месяца, а backend сохраняет только 12, 24, 36, 48, 60. Для роста
клиентов лучше, чтобы backend тоже сохранял заявки на 3-84 месяца.

## Критерии готовности

- `POST /api/credit-apply` для `c-01394`, 300000 рублей, 12 месяцев даёт
  положительное решение.
- `POST /api/credit-apply` для `c-01434`, 900000 рублей даёт отказ или встречное
  предложение.
- Объяснение отказа человеческое, по-русски, не короче 120 символов.
- Заявка сохраняется в backend.
- История заявок доступна из backend.
- В каталоге CIB есть кредитный продукт.
- Переводы продолжают работать.
- Ответ клиенту приходит быстро, желательно быстрее 1.5 секунды.
