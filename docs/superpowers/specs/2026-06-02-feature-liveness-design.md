# Якорь «фича живая» — проверка работоспособности добавленной фичи

**Дата:** 2026-06-02
**Статус:** дизайн → реализация
**Контекст:** на живом прогоне команда выкатила вкладку «Кредиты» в retail,
ручка оформления не работает (кредит взять нельзя), но LLM-судья начислил
клиентов в плюс. Судья поверил витрине (текст CONTRACT.md + вкладка в HTML),
ни разу не дёрнув саму ручку.

## Проблема

`feature_value` (scoring.py) начисляет ценность осей, как только
`feature_state in ("working", "partial")`. `partial` и `working` по ценности
**не различаются** — стадия лишь отделяет `absent` (ноль) от «фича есть».
`feature_state` ставится из diff контрактов + LLM-оси `completeness`, которые
LLM выводит из **текста** контракта и HTML. Реальный вызов новой ручки нигде
не делается. Итог: «витрина без функциональности» (вкладка есть, действие не
проходит) проходит как ценная фича.

Это асимметрия с якорем регрессии: регрессию **базовых** функций
(`assess_regression`) проверяем делом (реальный `POST /api/transfer`), а
**новую** фичу — только на слово.

## Решение: сигнал `feature_live ∈ {True, False, None}`

Симметричный якорь: реально выполнить главное новое действие фичи и оценивать
по фактическому ответу сервиса команды, а не по декларации.

Источник «что за ручки» — сам `CONTRACT.md`: воркшоп обязывает декларировать
каждую ручку (иначе соседний блок её не вызовет). Хардкода конкретных фич нет.

### Трёхуровневый, каждый уровень — фоллбэк следующего

1. **Обнаружение (детерминированно, без сети).** Парсим `### МЕТОД /путь` в
   текущих контрактах, вычитаем baseline → новые ручки раунда. Цель проверки —
   самая клиентская: приоритет `retail → cib → backend` (клиент ходит через
   мобильное приложение, оно транзитивно дёргает cib+backend).
2. **Существование (Tier 1, без LLM).** Дёргаем primary-ручку минимальным
   телом. `404`→ручки нет (`False`); `5xx`→выкачено и падает (`False`);
   `2xx`→предварительно живая (`True`); `4xx`-валидация (`400/422`)→ручка есть,
   но нужен валидный ввод → **неубедительно**, идём в Tier 2.
3. **Реальный вызов (Tier 2, LLM синтезирует тело).** LLM читает прозу
   контракта под ручкой + реальные seed-id клиентов/продуктов → валидное тело;
   probe выполняет. `2xx` + осмысленный ответ → `True`; `4xx/5xx/тело-ошибка`
   → `False`.

### Атрибуция вины (ключевое свойство безопасности)

`False` ставим **только** на реальный HTTP-ответ от сервиса команды. Падение на
**нашей** стороне (LLM сгенерил кривой JSON, наш таймаут, сеть) → фоллбэк на
сигнал нижнего уровня; нет ответа от команды → `feature_live = None`.

**`None` = «неизвестно» = скоринг как сейчас, без штрафа.** Мы никогда не
наказываем команду за сбой нашего инструмента. Гейт умеет только *запретить*
завышение при доказанной мёртвости.

## Интеграция в скоринг

* **Гейт ценности.** `feature_value(..., feature_live)`: при `False` оси не
  дают ценности (как `absent`). При `True`/`None` — поведение как сейчас.
* **Штраф витрины.** Если ручка доказанно мёртвая И это `5xx` (выкачено и
  падает на глазах клиента) — добавляем один `BROKEN_ENDPOINT_COST` к
  `outage_penalty` (как «сделано криво»). Чистый `404` (ручки нет) → только
  ноль ценности, без штрафа (клиент действия просто не получает).
* **Текст табло.** При `False` `_compose_reason` даёт детерминированную фразу
  «клиенты увидели новую возможность, но воспользоваться ей пока нельзя — она
  не работает», поверх — якорь регрессии базовых функций, если есть.

## Подача в LLM-судью (мягкий слой)

`snap["feature_probe"]` (метод/путь/статус/срез тела/вердикт) идёт в промпт
судьи как **детерминированные ДАННЫЕ** (как факты регрессии). Судья снижает
`completeness/client_value` и пишет точный человеческий reason. Детерминированный
гейт остаётся жёстким якорем независимо от того, что скажет LLM.

## Архитектура

* `probe_team(team, urls, repo, baseline_snap=None)` после чтения контрактов
  вызывает `assess_feature_liveness` и кладёт результат в `snap["feature_probe"]`
  — вся живая сеть остаётся в probe (как `regression`). `baseline_snap=None`
  (на самом замере baseline) → фичи нет, liveness не считается.
* `src/feature_probe.py` (новый): `parse_endpoints`, `discover_new_endpoints`,
  `classify_status` (чистые, тестируемые) + `assess_feature_liveness`
  (оркестрация Tier 1/2, fail-safe→None, `synth` инъектируется для тестов).
* `evaluate_round`/`judge` читают `snap.get("feature_probe")`.

## Безопасность и фоллбэки

* Любое исключение в liveness → `feature_live=None` → текущее поведение.
* Побочный эффект вызова новой ручки — тот же класс риска, что у уже
  существующего probe перевода (seed-данные, малые суммы).
* Холодный старт/таймаут → `None`, не «мертво».
* Стоимость: +1 LLM-вызов (синтез тела) и +1–2 HTTP-вызова **только** для
  команд с новым деплоем и новой ручкой; Tier 2 не запускается, если Tier 1
  уже дал вердикт (`404`/`5xx`/`2xx`).

## Тесты

* `test_feature_probe.py`: parse_endpoints (форматы заголовков), discover (diff,
  порядок блоков), classify_status (2xx/404/5xx/4xx/None), assess (Tier1 dead,
  Tier2 live через инъекцию synth, наша ошибка→None).
* `test_scoring.py`: `feature_value` с `feature_live=False`→0; True/None→как сейчас.
* `test_simulation.py`: мёртвая фича (feature_probe.False) не даёт плюса;
  `None` не меняет текущее поведение; 5xx-витрина уводит базу в минус.
